Fix SSH "Connection Refused" and "Timeout" Errors

SSH connection errors usually come down to one of four things: the service isn't running, the port is wrong, a firewall is blocking it, or you're connecting to the wrong address. Here's how to narrow it down fast.

Understand the Error

ErrorMost likely cause
Connection refusedSSH isn't running, or wrong port
Connection timed outFirewall blocking the connection
No route to hostWrong IP, or machine is offline
Host key verification failedServer fingerprint changed

Step 1 — Can You Reach the Server at All?

ping yourserver    # does it respond?

# If no ping response, the machine is offline, wrong IP, or ICMP is blocked
# Try connecting directly (console/VNC) if you can

Step 2 — Is SSH Running on the Server?

If you have console access:

# Check if sshd is running
sudo systemctl status sshd
sudo systemctl status ssh     # Debian/Ubuntu uses "ssh"

# Start it if it's stopped
sudo systemctl start sshd

# Enable so it starts on boot
sudo systemctl enable sshd

Step 3 — What Port Is SSH On?

# Check the configured port
grep Port /etc/ssh/sshd_config
# Default is 22 — if it's something else, use -p

ssh -p 2222 user@yourserver
# Verify something is actually listening on that port
sudo ss -tlnp | grep sshd
# or
sudo netstat -tlnp | grep :22

Step 4 — Is a Firewall Blocking the Port?

# UFW (Ubuntu/Debian)
sudo ufw status
sudo ufw allow 22/tcp    # or your custom port

# firewalld (Fedora/RHEL)
sudo firewall-cmd --list-all
sudo firewall-cmd --permanent --add-service=ssh
sudo firewall-cmd --reload

# iptables
sudo iptables -L INPUT -n | grep 22

If you're on a VPS or cloud server, also check the cloud provider's firewall/security group — it's separate from the OS firewall and often blocks everything by default.

Step 5 — Test From Another Machine

# Test if port 22 is reachable
nc -zv yourserver 22
# or
telnet yourserver 22

# Connection refused = port reached but service rejected it
# Timeout = firewall blocking

Fix: Host Key Verification Failed

This happens when the server's key changes — after a reinstall, or if you reused an IP address:

ssh-keygen -R yourserver
# or
ssh-keygen -R 192.168.1.100

# Then reconnect and accept the new fingerprint

Fix: Too Many Authentication Failures

# SSH tried too many keys from your agent
ssh -o IdentitiesOnly=yes -i ~/.ssh/id_rsa user@yourserver

Debug Mode

# Add -v for verbose output — shows exactly where it fails
ssh -v user@yourserver
ssh -vvv user@yourserver    # even more detail

Check Server Logs

# On the server
sudo journalctl -u sshd -f    # follow live
sudo tail -f /var/log/auth.log    # Debian/Ubuntu
sudo tail -f /var/log/secure      # Fedora/RHEL
